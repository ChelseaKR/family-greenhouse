# Internationalization

How UI strings work in this repo, and the gates that keep them honest. The
format decision (i18next-native JSON catalogs, no ICU MF1) is recorded in
[ADR 0007](adr/0007-i18n-json-catalogs-native-format.md); the portfolio-wide
requirements live in `STANDARDS/INTERNATIONALIZATION-STANDARD.md`.

## Where strings live

```
frontend/src/i18n/
├── index.ts                     # i18next bootstrap, language detection, shipping gate
├── format.ts                    # Intl.* date/number/currency helpers
├── coverage.ts                  # translated-share measurement (unit-test gate)
├── legalCatalog.ts              # on-demand loader for the legal.* fragment
├── legalCatalogChunk.ts         # the deferred chunk (dynamic import only)
├── nonEnglishCatalog.ts         # on-demand loader for every non-English catalog
└── locales/
    ├── en/
    │   ├── translation.json     # source locale — canonical key set
    │   └── legal.json           # deferred legal.* fragment (same gates)
    └── es/
        ├── translation.json     # Spanish catalog (same keys, gate-enforced)
        ├── legal.json           # Spanish legal.* fragment
        └── translation.todo.json# untranslated/intentionally-equal markers
```

- Catalogs are i18next-standard per-locale namespace files
  (`<lng>/<namespace>.json`, single `translation` namespace today) and are the
  **single source of truth** for user-facing copy. Components render them via
  `useTranslation()` / `t('feature.key')`.
- **Deferred fragment:** `<lng>/legal.json` holds the 101 privacy / terms /
  support / account-deletion keys and is _not_ loaded at startup.
  `legalCatalog.ts` merges it into the same `translation` namespace with
  `addResourceBundle` when a legal route loads, and `App.tsx` awaits that inside
  the route's `React.lazy()` factory so the copy is registered before the page
  mounts (navigation, hydration of a prerendered page, and the build-time
  prerender alike). Keys stay `legal.*`-rooted, so call sites are identical
  either way. It exists because that prose is ~37 kB of copy that four rarely
  visited routes read — see `_size-limit-note-0-23-deferred-legal-catalog` in
  `frontend/package.json`. Every gate below covers it: `check-i18n-catalogs.mjs`
  runs the same checks over both files, and
  `frontend/tests/unit/i18n/legalCatalog.test.ts` fails if the fragment is
  imported eagerly or folded back into `translation.json`.
- Interpolation is i18next `{{var}}`; plurals are JSON-v4 CLDR suffixes.
  Always write explicit `_one` / `_other` (and whatever else the locale's
  CLDR rules require — Spanish also needs `_many`); never mix a bare key with
  suffixed forms of the same key.
- Dates, numbers, and currency never go through string concatenation — use
  `src/i18n/format.ts` (`Intl.*`, locale-aware).

## Adding or changing strings

1. Add the key to `en/translation.json` (English is the canonical key set), or
   to `en/legal.json` if it is a `legal.*` key.
2. Add the same key to **every** other locale. If you can't supply a real
   translation, copy the English value **and list the key in that locale's
   `translation.todo.json` under `todo`** — that is the untranslated-marker
   convention. Never machine-translate, and never leave an English value
   undeclared (the gate fails it as a silent fallback).
3. If a translation is genuinely identical to English (e.g. es `"No"`), list
   it under `intentionallyEqual` instead.
4. When a real translation lands, remove the key from `todo` — stale markers
   fail the gate too.

## Gates (merge-blocking; CI job `Lint`, also in `npm run verify`)

Run locally with `npm run i18n:check` (repo root or `frontend/`).

"Merge-blocking" was not true until CICD-467. These two scripts ran in a
separate `i18n Gates` job that is **not** one of the required status checks in
`.github/rulesets/main.json`, so every check in the table below could go red
without stopping a merge. They now run in `Lint`, which is required, and
`scripts/check-no-silenced-gates.mjs` fails the build if either one is moved
back into a job GitHub does not require.

| Check                                                                                                                                   | Script                                         | Standard          |
| --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ----------------- |
| Key parity — every logical key in every locale                                                                                          | `frontend/scripts/check-i18n-catalogs.mjs`     | G6                |
| Placeholder parity — identical `{{var}}` sets per key across locales                                                                    | same                                           | G5                |
| Plural categories — exactly the CLDR categories each locale requires                                                                    | same                                           | G5                |
| TODO markers — English-valued entries declared in `translation.todo.json`; no stale markers                                             | same                                           | (repo convention) |
| BCP-47 — locale dirs + `index.html` root `lang` well-formed/canonical                                                                   | same                                           | G3                |
| UTF-8 — every git-tracked text file strict-decodes                                                                                      | same                                           | G1                |
| No new hardcoded JSX text — per-file ratchet against `frontend/scripts/i18n-hardcoded-baseline.json`                                    | `frontend/scripts/check-hardcoded-strings.mjs` | G2                |
| No new hardcoded UI **attributes** (`aria-label`, `alt`, `title`, `placeholder`, …) — second per-file ratchet in the same baseline file | same                                           | G2                |

### The hardcoded-string ratchets

The scanner walks `frontend/src` twice over the same AST and keeps two
independent per-file ratchets in `frontend/scripts/i18n-hardcoded-baseline.json`
(curated long-form content — blog, help, care guides, changelog — is excluded
from both as a separate translation workstream):

| Baseline key | What it counts                                                                                                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `files`      | English in JSX **text nodes** (418 at first baseline, 329 today).                                                                                                                                                                             |
| `attributes` | English **string literals** in the attributes a user actually hears or reads: `aria-label`, `aria-description`, `aria-placeholder`, `aria-roledescription`, `aria-valuetext`, `alt`, `title`, `label`, `placeholder` (145 at first baseline). |

A file may never exceed either baseline, and when you migrate strings to the
catalog you must lower the baseline in the same PR
(`node scripts/check-hardcoded-strings.mjs --update-baseline` after reducing —
the diff shows counts only going down). An attribute whose value is an
expression (`aria-label={t('a.b')}`) is not counted: it is already going
through the catalog, or it is dynamic.

Non-linguistic attributes — `role`, `id`, `type`, `href`, `to`, `data-testid`,
`autoComplete`, `inputMode`, `pattern` — are machine-facing and deliberately
out of scope.

**What ESLint does and does not do here.** `eslint-plugin-i18next`'s
`no-literal-string` is enrolled for `src/features/settings/PreferencesSettings.tsx`
and `src/features/legal/**` only, and it runs with `markupOnly: true` — which
restricts it to JSX text nodes, the same scope as the scanner above. Its
`ignoreAttribute` option is an **exclusion** list (`aria-label` and
`placeholder` are on it), not a coverage list. It therefore contributes no
attribute coverage at all. This section used to say the opposite, and
`check-hardcoded-strings.mjs` used to defer attributes to it, so each gate
named the other as the owner and neither checked — which is why the attribute
ratchet now lives in the script that already has a ratchet mechanism. ESLint
has none, so enrolling the rule repo-wide would hard-fail on existing debt
instead of ratcheting it down.

## Locales and shipping

`en` and `es`.

### Shipping status: Spanish is a staged asset, not a shipped feature

**No user can select Spanish in any deployed environment, and that is a
decision nobody has made yet rather than a property of the catalogs.**
`VITE_ENABLE_NON_ENGLISH_LOCALES` is set in no workflow and no `.env*.example`,
so `SUPPORTED_LANGS` collapses to `['en']` everywhere, the picker in
`PreferencesSettings` is hidden, and `src/i18n/index.ts` pulls anyone with a
stored `es` preference back to English. #467 is where this is tracked.

What is _not_ the blocker: coverage. `es` is at **99.3% (1344/1354 keys)** with
**zero missing keys**, measured by `tests/unit/i18n/localeCoverage.test.ts`,
which now enforces the 95% bar on every run instead of only on a build that
flips the flag. The ten values that equal the English source are enumerated as
`intentionallyEqual` in `locales/es/translation.todo.json`; the six `todo`
entries are `_many` plural forms with no English counterpart, which only render
for counts ≥ 1,000,000.

What _is_ the blocker is a shipping decision with a product surface attached:

- a way for a user to find Spanish at all — a switcher in the public shell, or
  `navigator.language` detection, neither of which exists;
- `/es/*` routes, `hreflang`, and Spanish entries in `sitemap.xml`, none of
  which exist (`scripts/prerender.mjs` renders `publicRoutePaths()` in English
  and `index.ts` pins the SSR pass to `lng: 'en'`);
- native-speaker review of the catalog, and legal review of `legal.json` before
  `REVIEWED_LEGAL_LOCALES` can list `es`;
- the backend copy, which is English regardless of this flag (household
  invitation emails, chat safety messages);
- the store listings, which `scripts/validate-store-release.mjs` hardcodes to
  `en-US.json`.

Until that decision is made, treat the catalogs as staged: keep them
gate-complete, keep them off the bytes every visitor downloads, and do not
describe Spanish as a shipped feature anywhere user-facing.

### What "staged" costs, and what it must not cost

Spanish used to be imported statically by `src/i18n/index.ts` and pinned by
`vite.manualChunks.ts` into the `i18n` chunk that `index.html` modulepreloads,
so **every visitor downloaded the whole Spanish catalog on the startup path to
reach a language the UI would not offer them** — 86.6 kB of JSON, measured at
42.3 kB brotli inside a 228.0 kB critical path (#467 §2).

`src/i18n/nonEnglishCatalog.ts` now `import()`s each non-English catalog on
demand, and the chunk rule names `locales/en/translation.json` specifically so
a pattern cannot quietly sweep the deferred catalogs back onto the startup
path. `tests/unit/i18n/nonEnglishCatalog.test.ts` holds both halves.

Two things to know before changing this:

- **A locale-wide `manualChunks` pattern undoes the split silently.** The
  dynamic import still resolves and Spanish still renders; only the bytes move.
  Same trap `legal.json` documents.
- **`?url` + `fetch` does not currently work.** Emitting the catalogs as
  `.json` assets is the standard i18next shape, and it is the only shape that
  also moves the `All JS combined` budget (which globs `dist/assets/*.js` and
  counts bytes _emitted_, so it is immune to code splitting) — measured at
  501.33 → 481.65 kB brotli. But all three deploy paths
  (`.github/workflows/cd-production.yml`, `cd-staging.yml`, `scripts/deploy.sh`)
  sync `dist` with `--exclude "*.json"` and no compensating `--include`, so a
  JSON file under `dist/` is never uploaded. The catalog would 404 for every
  user who opted in, and neither the build nor the size gate would notice.
  Fix the deploy exclusion first; then the `?url` form is strictly better.

### Trying Spanish without a rebuild

`?locales=on` enables the non-English locales on the current device and
persists the choice in `localStorage`; `?locales=off` clears it again. Neither
overrides the build-time flag, which is the "ship it to everyone" switch.

The legal pages (`src/features/legal/`) render entirely from `legal.*` keys,
so they ship behind the same gate. Their Spanish is a draft that has had
neither native-speaker nor legal review: `REVIEWED_LEGAL_LOCALES` in
`src/features/legal/reviewedLocales.ts` lists the locales whose legal text has been signed off, and
every other non-English locale renders a "draft — the English version governs"
notice above the text. Add a locale there only after both reviews.

**Adding a locale:** create `locales/<bcp47-tag>/translation.json` **and
`legal.json`** with every key (English values + full `todo` sidecar listing is
acceptable as a scaffold), add the tag to `ALL_LANGS` in `src/i18n/index.ts` and
to `LEGAL_LOCALES` in `src/i18n/legalCatalog.ts`, add a loader entry to
`CATALOG_LOADERS` in `src/i18n/nonEnglishCatalog.ts` (a literal `import()` of a
literal path — anything else folds the catalog into the startup chunk), and —
if it's RTL — to `RTL_LANGS`. The gates enforce the rest from the first
commit.
